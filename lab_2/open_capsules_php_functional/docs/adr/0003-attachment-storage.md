# ADR-0003. Хранение вложений TimeCapsule

- Статус: принято (ЛР4)
- Дата: 2026-10-25

## Контекст

В ЛР2 и ЛР3 вложения находились в `storage/uploads` на EBS томе `app-server`. Потеря этого экземпляра или замена его новым сервером могла лишить пользователей доступа к файлам. Для дальнейшего масштабирования приложение должно хранить вложения вне локального диска и не давать прямой публичный доступ к ним.

## Решение

Хранить вложения в бакете `timecapsule-dev-uploads-dumkaguv` региона `eu-central-1` под префиксом `uploads/`. PHP приложение использует AWS SDK с временными учётными данными роли EC2 `timecapsule-dev-app-role`. Роль разрешает только `GetObject`, `PutObject` и обычный `DeleteObject` для `uploads/*`; список объектов и удаление конкретных версий ей не нужны.

При создании капсулы `storage_save()` записывает объект с исходным MIME типом под случайным ключом. После проверки прав пользователя и времени открытия капсулы `storage_stream()` отправляет HTTP 302 на подписанный `GetObject` URL, действующий пять минут. В URL подписаны ключ объекта, срок действия и параметры ответа с MIME типом, способом показа и исходным именем файла. `storage_delete()` выполняет обычный `DeleteObject`: при включённом версионировании S3 создаёт маркер удаления, а прежняя версия остаётся восстанавливаемой.

## Рассмотренные варианты

| Вариант | Преимущества | Недостатки |
| --- | --- | --- |
| EBS том app-server | Простая файловая система и минимальные изменения кода | Вложения привязаны к одному экземпляру и зоне доступности; для замены сервера нужны перенос тома или восстановление из снимка; нескольким серверам неудобно использовать один том |
| Amazon EFS | Общая файловая система для нескольких серверов, почти без изменений интерфейса хранения | Нужны точки монтирования, сетевой доступ и управление правами POSIX; постоянные расходы на хранение и запросы; приложение остаётся зависимым от доступности монтирования |
| Amazon S3 | Объектное хранение отдельно от EC2; один бакет доступен нескольким серверам; версионирование, правила жизненного цикла и подписанные URL | Нужно изменить модуль хранения; нет обычных файловых операций и транзакции между БД и S3; нужны контроль прав IAM и учёт стоимости версий и запросов |

Выбран S3: приложение работает с вложениями как с объектами, а не изменяет их на месте. Небольшой модуль `src/storage.php` изолирует отличие S3 от локального диска.

## Последствия

- Пользователь сначала обращается к приложению. Оно проверяет доступ к капсуле и время открытия, затем выдаёт подписанный URL. Браузер скачивает файл непосредственно из S3; ссылка перестаёт работать через пять минут или раньше при прекращении действия временных учётных данных роли. Получивший ссылку в это время также сможет скачать файл, поэтому приложение не публикует её в постоянном хранилище.
- Публичный доступ к бакету закрыт, бакет требует HTTPS, а роль ограничена префиксом `uploads/`. Версионирование защищает от ошибочного обычного удаления. Правило жизненного цикла переводит подходящие неактуальные версии в Standard-IA через 30 дней и удаляет старые через 90 дней, оставляя две последние неактуальные версии; оно также отменяет незавершённые multipart загрузки через семь дней. Это ограничивает рост занимаемого места, но за версии и запросы всё равно начисляется плата.
- При появлении нескольких `app-server` за балансировщиком все экземпляры смогут читать и записывать один бакет с одинаковой ролью и конфигурацией. Локальный каталог вложений и его синхронизация между серверами больше не нужны. База данных и сессии при этом остаются отдельными вопросами масштабирования.
- S3 хранит данные в пределах выбранного региона. Для переживания отказа всего `eu-central-1` потребуется репликация в другой регион, отдельная точка доступа и план переключения приложения и базы данных.
