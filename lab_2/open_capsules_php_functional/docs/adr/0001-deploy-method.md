# ADR-0001. Развёртывание TimeCapsule с помощью deploy.sh

- Статус: принято
- Дата: 2026-10-03

## Контекст

Приложение TimeCapsule развёрнуто на одном экземпляре Amazon EC2 с Amazon Linux 2023. На этом же сервере работают nginx, PHP-FPM и PostgreSQL. Исходный код хранится в публичном репозитории [dumkaguv-cloud/timecapsule](https://github.com/dumkaguv-cloud/timecapsule).

Для выпуска новой версии необходимо получить изменения из GitHub, установить зависимости, создать недостающие таблицы базы данных и перезагрузить PHP-FPM. Выполнение этих действий вручную при каждом обновлении повышает риск пропустить шаг. Для учебного проекта нужен простой и повторяемый процесс, который можно запускать через SSH.

## Решение

Использовать вариант B: скрипт `~/deploy.sh` на EC2. Разработчик изменяет код на своём компьютере, создаёт коммит и отправляет его в GitHub командой `git push`. После этого запускает скрипт на сервере через SSH.

Скрипт переходит в `/var/www/timecapsule` и последовательно выполняет:

1. `git pull --ff-only` — получает изменения из репозитория без создания merge-коммита. При расхождении истории обновление прекращается.
2. `composer install --no-dev --optimize-autoloader --no-interaction` — устанавливает зависимости приложения.
3. `php bin/init-db.php` — создаёт недостающие таблицы PostgreSQL.
4. `sudo systemctl reload php-fpm` — перезагружает PHP-FPM.

В скрипте используется `set -euo pipefail`, чтобы при ошибке не продолжать следующие этапы. После успешного выполнения выводится последний коммит: по нему можно определить установленную версию.

Сервер получает код публичного репозитория по HTTPS. Для этого ему не нужны учётные данные с правом записи в GitHub. Файл `.env` и загруженные пользователями файлы хранятся отдельно от отслеживаемого Git исходного кода и не включаются в коммиты.

## Рассмотренные альтернативы

| Способ | Преимущества | Недостатки и причина выбора |
| --- | --- | --- |
| Копирование через `scp` | Подходит для первоначальной загрузки нескольких статических файлов. | Нужно самостоятельно выбирать файлы и следить за полнотой обновления. Сложнее установить, какой версии репозитория соответствует код на сервере. Не выбран для обновления приложения. |
| `git pull` и остальные команды вручную на сервере | Код поступает из GitHub, доступна история изменений, дополнительный скрипт не требуется. | При каждом обновлении приходится повторять команды; можно пропустить установку зависимостей или подготовку базы данных. Не выбран как основной способ. |
| Скрипт `deploy.sh`, запускаемый через SSH | Фиксирует порядок команд, сокращает ручные действия и показывает этап сбоя. | Требует поддерживать скрипт при изменении процесса установки. Выбран как достаточный для одного учебного сервера. |

## Последствия

Положительные:

- Все обновления выполняются одной и той же последовательностью команд.
- Код доставляется из GitHub; установленную версию можно сопоставить с коммитом.
- Разработчик запускает деплой одной командой через SSH.
- Серверу не требуется доступ на запись в репозиторий.

Ограничения и риски:

- Запуск остаётся ручным: `git push` сам по себе не обновляет приложение на EC2.
- Скрипт не выполняет автоматические тесты и не гарантирует работоспособность всех страниц после обновления.
- Обновление не атомарное. Во время замены файлов или установки зависимостей посетитель может получить ошибку.
- Прекращение скрипта при ошибке не отменяет уже выполненные действия. Сервер может остаться в частично обновлённом состоянии.
- Откат кода выполняется через `git revert`, отправку нового коммита и повторный деплой. Он не восстанавливает автоматически данные или прежнюю схему базы.
- Приложение, база данных и пользовательские файлы находятся на одном EC2. Сбой экземпляра затрагивает весь сервис; выбранный способ деплоя не обеспечивает резервное копирование или отказоустойчивость.
